# Attribution Hazards

> The ways a migrated template lies about which lines a field produced — every one of them
> byte-perfect, every one of them invisible to a golden-output suite.

[README.md](./README.md) explains what provenance is. [line-attribution.md](./line-attribution.md)
explains the builders and the one rule they carry. This page is what the first real migration
learned: the Stellar generator's sixteen source files moved onto the builders without changing a
single generated byte, and still produced six wrong attributions on the way, in four distinct
classes — plus a fifth class found later when a list-scan left its root on the emit.

If you are migrating a generator, read this before you start. Every hazard below is reproduced as a
runnable snippet you can paste into a scratch file, and in every one the broken and fixed versions
produce **identical text**. That is the point.

## Two proofs, not one

A migration has to prove two independent things, and only one of them is easy.

1. **The bytes did not move.** Every generated file is character-for-character what it was.
2. **The attribution is honest.** Every recorded range holds lines the field actually determines.

Neither implies the other, and a golden-output suite only sees the first. Goldens compare
`result.files`; `result.provenance` is not in them, so no amount of green tells you the ranges are
right. Recording is designed never to change output, which means every attribution bug you will
ever write is, by construction, byte-neutral.

The demonstration that settled this: widening one range in the workspace manifest so it covered the
fixed core crates as well as the configured module left all 891 goldens green. It was caught only by
a check that read the provenance.

```ts
import { generate } from '@openzeppelin/codegen-rwa-stellar';
import type { RWAConfig } from '@openzeppelin/rwa-config';

export function recordingChangesNothing(config: RWAConfig): boolean {
  const off = generate(config);
  const on = generate(config, { recordProvenance: true });
  return (
    JSON.stringify(off.files) === JSON.stringify(on.files) &&
    off.metadata.configHash === on.metadata.configHash
  );
}
```

That function returns `true`, and it will keep returning `true` however wrong your ranges are. Write
the second proof.

## The hazard catalogue

Five classes. The first four are real defects from the Stellar migration, reduced to the smallest
program that reproduces them. The fifth is the residual after hazard 3's test-before-resolve fix:
walking a list only to find a match still records the list root.

### 1. The iterator drain

**`for…of` over a config array attributes the loop to the heading below it.**

A `for…of` loop reads its iterator once more than it yields — the final read that reports "done"
fires _after_ the last body emission. The builder attributes every read to the next emission that
produces bytes, so that trailing read lands on whatever comes next: the following section's heading,
or a blank separator line.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  topics: Array<{ id: number }>;
  issuers: Array<{ addr: string }>;
}

export function broken(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);

  b.line(`# Topics (${b.config.topics.length})`);
  for (const t of b.config.topics) b.line(`add_topic ${t.id}`);
  b.line(`# Issuers (${b.config.issuers.length})`);
  for (const i of b.config.issuers) b.line(`add_issuer ${i.addr}`);

  return b.text();
}
```

```text
1-1  [topics]                  -> "# Topics (2)"
2-2  [topics, topics[0].id]    -> "add_topic 1"
3-3  [topics, topics[1].id]    -> "add_topic 2"
4-4  [issuers, topics]         -> "# Issuers (1)"   ← the drain
5-5  [issuers, issuers[0].addr]-> "add_issuer A"
```

Line 4 claims `topics`. A user asking what the topics field determines is shown the issuers
heading — a line that has nothing to do with it.

**The fix: index against a count you observed.** `observe` records what the count read without
attributing it to a line, and you hand those paths to the heading the count actually shapes. Each
element is then read at the line it produces.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  topics: Array<{ id: number }>;
  issuers: Array<{ addr: string }>;
}

export function fixed(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);

  const topicCount = b.observe((c) => c.topics.length);
  const issuerCount = b.observe((c) => c.issuers.length);

  b.line(`# Topics (${topicCount.value})`, topicCount.paths);
  for (let i = 0; i < topicCount.value; i += 1) b.line(`add_topic ${b.config.topics[i].id}`);
  b.line(`# Issuers (${issuerCount.value})`, issuerCount.paths);
  for (let i = 0; i < issuerCount.value; i += 1) b.line(`add_issuer ${b.config.issuers[i].addr}`);

  return b.text();
}
```

```text
1-1  [topics]           -> "# Topics (2)"
2-2  [topics[0].id]     -> "add_topic 1"
3-3  [topics[1].id]     -> "add_topic 2"
4-4  [issuers]          -> "# Issuers (1)"
5-5  [issuers[0].addr]  -> "add_issuer A"
```

Identical bytes, and the drain is gone. Note the second improvement: the body lines no longer carry
the bare `topics` array path either, so a query for `topics[1].id` stops matching line 2.

Any construct that reads a config container one final time after its last emission has this shape.
`for…of`, `Array.prototype.entries()`, a generator delegating to a config array, and a spread
evaluated lazily are all the same hazard.

### 2. The block that can render empty

**A span that may render nothing must not carry its own paths.**

An emission of only line terminators attributes to the single line it _starts_ on — which belongs to
whatever is adjacent. So an interpolation that renders to `''` on some configurations contributes no
characters but still hands its paths to the block, and the block's range covers its neighbours.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  modules: Array<{ id: string }>;
}

const renderModules = (c: Config): string => c.modules.map((m) => `- ${m.id}`).join('\n');

export function broken(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);
  const modules = b.observe(renderModules);

  b.line('# Project');
  // `modules` and the notes share a line, so they cannot be split into two blocks.
  b.block(
    `${modules.value ? `${modules.value}\n` : ''}## Notes\n\nStable platform note.`,
    modules.paths
  );

  return b.text();
}
```

With `modules: []` the emitted text is just the notes, and the recorded range is:

```text
2-4  [modules]  -> "## Notes"
```

Ticking a compliance module is reported as rewriting the platform note.

**The fix: an emptiness predicate at the call site.** A span contributes its paths only when it holds
a character other than `'\n'` or `'\r'` — the same rule the builder uses to trim a range.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  modules: Array<{ id: string }>;
}

const renderModules = (c: Config): string => c.modules.map((m) => `- ${m.id}`).join('\n');

/** `true` when `span` holds at least one character a range would attribute. */
function holdsContent(span: string): boolean {
  for (const character of span) if (character !== '\n' && character !== '\r') return true;
  return false;
}

export function fixed(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);
  const modules = b.observe(renderModules);

  b.line('# Project');
  b.block(
    `${modules.value ? `${modules.value}\n` : ''}## Notes\n\nStable platform note.`,
    holdsContent(modules.value) ? modules.paths : []
  );

  return b.text();
}
```

With `modules: []` the block now records **no range at all**; with one module selected it records
`2-5 [modules, modules[0].id]` covering the rendered list. Bytes unchanged in both cases.

**A block can have more than one empty span, and suppressing one is not enough.** The real instance
of this had two independent sources in a single block: a rendered module list, and — a few lines
below it, interpolated into the same template literal — a warning renderer that read the same array
to decide whether to warn and returned `''` when it had nothing to say. Suppressing the first left
the check still failing, which is how the second was found. Every possibly-empty interpolation in a
block needs the predicate, not just the one you noticed.

### 3. The helper that reads more than you asked for

**Building a whole descriptor to read one field off it attributes everything the descriptor
touched.**

Recording sees property reads, not intent. A helper that assembles a rich object is a dependency on
every field it consulted, even if the caller uses one constant member of the result.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  token: { name: string; symbol: string };
  roles: Array<{ symbol: string }>;
}

const CRATE_NAME = 'rwa_token';

/** Pre-existing helper, reused by templates that want the whole descriptor. */
const buildTokenDescriptor = (c: Config): { crateName: string; displayName: string } => ({
  crateName: CRATE_NAME,
  displayName: `${c.token.name} (${c.token.symbol}) ${c.roles.map((r) => r.symbol).join(' ')}`,
});

export function broken(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);
  const crates = b.observe((c) => [buildTokenDescriptor(c).crateName]);

  b.line('verify_wasm_artifacts() {');
  b.line(`  test -f target/${crates.value[0]}.wasm || exit 1`, crates.paths);
  b.line('}');

  return b.text();
}
```

```text
2-2  [roles, roles[0].symbol, roles[1].symbol, token.name, token.symbol]
     -> "  test -f target/rwa_token.wasm || exit 1"
```

A WASM preflight check containing no token name and no role now claims both. In the real generator
this was a preflight block of around thirty lines, growing with the module list.

**The fix: read the constant, not the descriptor.** If the value you need does not depend on config,
do not go through config to get it.

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  token: { name: string; symbol: string };
  roles: Array<{ symbol: string }>;
}

const CRATE_NAME = 'rwa_token';

export function fixed(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);

  b.line('verify_wasm_artifacts() {');
  b.line(`  test -f target/${CRATE_NAME}.wasm || exit 1`);
  b.line('}');

  return b.text();
}
```

No range at all, which is the honest answer: nothing in that block depends on config.

This is the hardest class to spot, because the offending helper usually predates the migration, is
shared by several templates, and is correct for all of them. Audit what each `observe` callback
_reaches_, not what it returns.

**It is also the class that recurs the most, because the over-reading helper is shared.** The
Stellar generator had four more instances after the crate-name one above, all of them the same
sentence — _a question about one thing, answered by building the descriptor for everything_:

| Helper                         | Asked for                      | Also read                                       | Attributed to                         |
| ------------------------------ | ------------------------------ | ----------------------------------------------- | ------------------------------------- |
| `getConfiguredRoleSymbol`      | the symbol guarding one method | every role's symbol **and member addresses**    | all 20 method guards in `contract.rs` |
| `getAdditionalRoleAssignments` | the non-manager roles          | the manager's member addresses                  | the role constants, params and grants |
| `getManagerAddress`            | the manager's address          | every other role's member addresses             | `MANAGER="…"` in `deploy.sh`          |
| `getDeployGuidance`            | an admin address               | `token.initialSupply` and every module's config | a 78-line README deploy section       |

The first three share one root: `getResolvedRoleAssignments` normalizes **every** role — name,
symbol and address list — and callers then `.find()` or `.filter()` the result. Filtering after
resolution is what makes a question about one role a dependency on all of them. The fix in each
case was to test first and resolve second, so only the role actually being asked about has its
symbol and members read.

The user-visible symptom was stark: focusing one operator role's address list highlighted 23
ranges in `contracts/rwa-token/src/contract.rs`, including `#[only_admin]` on `mint`, `burn`,
`set_compliance` and `set_identity_verifier` — methods that role does not guard. Changing the
address moved **zero** bytes of that file. After the fix, 7 ranges remain, and every one of them
disappears when the role loses its members.

### Existence is a dependency; the value is a different one

That fix leaves a distinction worth stating, because it decides what "wrong" means here.

`contract.rs` depends on **whether** a role has members — empty the list and the role constant,
the constructor parameter, the grant and the two `#[only_role]` guards all vanish. It does not
depend on **which** address is in the list; that reaches `deploy.sh`, where it is passed to
`grant_role_members`. Both are real dependencies of different files, and only one of them is a
dependency on the value.

A mutation that swaps one valid address for another therefore moves nothing in `contract.rs`, and
an oracle armed only with value mutations reports the honest existence-dependent ranges as broken
while missing the over-claims it was built to catch. Membership arrays and optional scalars need
**both** kinds of mutation — a different value, and no value at all. This is the concrete reason
the mutation set is per-path and plural.

### 4. The helper that returns a joined string

**One emission is one range, so a helper that returns a joined block gives every field in it the
same lines.**

```ts
import { createLineBuilder } from '@openzeppelin/codegen-core';
import type { LineSink, ProvenanceScope } from '@openzeppelin/codegen-core';

interface Config {
  modules: Array<{ id: string }>;
  topics: Array<{ id: number }>;
  issuers: Array<{ addr: string }>;
}

const buildPostDeploy = (c: Config): string =>
  [
    `configure_module ${c.modules[0].id}`,
    `add_topic ${c.topics[0].id}`,
    `add_issuer ${c.issuers[0].addr}`,
  ].join('\n');

export function broken(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);
  b.line('# Post-deploy');
  b.line(buildPostDeploy(b.config));
  return b.text();
}

/** The fix: hand the helper the sink and let it emit per site. */
const emitPostDeploy = (sink: LineSink, c: Config): void => {
  sink.line(`configure_module ${c.modules[0].id}`);
  sink.line(`add_topic ${c.topics[0].id}`);
  sink.line(`add_issuer ${c.issuers[0].addr}`);
};

export function fixed(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);
  b.line('# Post-deploy');
  emitPostDeploy(b, b.config);
  return b.text();
}
```

```text
broken:  2-4  [issuers[0].addr, modules[0].id, topics[0].id]  -> "configure_module m0"

fixed:   2-2  [modules[0].id]    -> "configure_module m0"
         3-3  [topics[0].id]     -> "add_topic 1"
         4-4  [issuers[0].addr]  -> "add_issuer A"
```

Clicking any one of the three highlighted all three. The real instance was the whole post-deploy
configuration section — dozens of lines — shared by compliance modules, claim topics and trusted
issuers.

Threading the sink costs no bytes: the builder joins its elements with the same separator the helper
was joining with. A helper that takes a `LineSink` is also the one that stays honest as it grows,
because each new line lands where it is written.

### 5. The list scan that leaves its root on the emit

**Scanning a list only to find a match still records the list root — and child-path matching then
lights every Addresses (or sibling) query against those emits.**

Hazard 3 fixed over-reading every role's addresses: `findRoleWithMembers` (and the same
test-before-resolve shape) stops resolving siblings you did not ask about. That fix is necessary
and insufficient. Walking `config.accessControl.roles` to compare names still records
`accessControl.roles` on the observe window. Prefix matching is unchanged and correct: a recorded
list root answers a query for `accessControl.roles[0].addresses`. Focusing one role's Addresses
field therefore lights ranges that only consulted the list for a name match — lines that do not
move when that role's members change.

This is **not** a matching bug. Do not teach `matchesConfigPath` to ignore list roots; that would
break every legitimate parent-read → child-query case elsewhere. Fix attribution at emit time.

```ts
import { createLineBuilder, omitExactConfigPath } from '@openzeppelin/codegen-core';
import type { ConfigPath, ProvenanceScope } from '@openzeppelin/codegen-core';

interface Role {
  name: string;
  symbol: string;
  addresses: string[];
}

interface Config {
  accessControl: { roles: Role[] };
}

const ROLES_LIST: ConfigPath = 'accessControl.roles';

/** Pre-existing scan: tests first, then resolves one role — hazard 3's fix. */
const findRoleWithMembers = (
  c: Config,
  predicate: (role: Role) => boolean
): Role | undefined => c.accessControl.roles.find(predicate);

export function broken(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);

  const guard = b.observe((c) => {
    const role = findRoleWithMembers(c, (r) => r.name === 'minter');
    return role?.symbol;
  });

  if (guard.value !== undefined) {
    // The observe walked ROLES_LIST to find a match. Leaving it on the emit
    // makes every Addresses child query match these lines.
    b.line(`#[only_role(${guard.value})]`, guard.paths);
  }

  return b.text();
}

export function fixed(scope: ProvenanceScope<Config>): string {
  const b = createLineBuilder(scope);

  const guard = b.observe((c) => {
    const role = findRoleWithMembers(c, (r) => r.name === 'minter');
    return role?.symbol;
  });

  if (guard.value !== undefined) {
    // Lookup scan: omit the list root. The emit depends on the matched symbol,
    // not on the whole list. Matching stays put.
    b.line(`#[only_role(${guard.value})]`, omitExactConfigPath(guard.paths, ROLES_LIST));
  }

  return b.text();
}
```

Identical bytes. The broken emit still carries `accessControl.roles`; the fixed emit does not.
`omitExactConfigPath` drops by **exact string equality** only — it never parses, never calls
`matchesConfigPath`, and never strips child paths such as `accessControl.roles[0].addresses`.

**Do not omit when the emit depends on the whole list.** Iterating members, joining addresses,
emitting a count derived from the array length — those are honest list-root dependencies. Leave
the root on the path list. The helper is opt-in at the scan site, never an automatic post-`drain`
filter, and never a second matching system.

Hazard 3 and hazard 5 are complementary: test-before-resolve stops over-reading sibling values;
emit-time omit drops the residual list-root left by walking the array. The historical "7 ranges
remain" figure under hazard 3 is a past measurement, not an acceptance bar — re-measure which
ranges disappear when the focused role loses its members.

## The standing rule: sweep the class, not the instance

**When you find a hazard, sweep every sibling occurrence in the file before moving on.**

This is the most transferable thing the Stellar migration produced, and it was learned the
expensive way. The last two defects to be fixed were both _second_ occurrences of a class already
fixed a few lines away in the same file:

- The iterator drain was fixed in the trusted-issuers loop. The claim-topics loop immediately above
  it was left alone — in a function whose own doc comment describes the hazard, with the observed
  count and paths already threaded in by the caller and simply never read.
- The empty-block predicate was applied to the workspace manifest's member groups and to one span of
  the readme block. The second possibly-empty interpolation _in that same block_ was not considered
  until suppressing the first left the check red.

Fixing the instance is not fixing the class. When a hazard is confirmed, grep the file for the shape
— every `for…of` over a config array, every possibly-empty interpolation in a block, every helper
that assembles a descriptor, every list scan that only needed a match — and check each one before
you claim the fix is done.

## Finding these on purpose

Containment asks whether a field's value appears inside the range it claims. That is necessary and
far too weak: the drain, the empty block and the over-reading helper all pass it. The question worth
asking is whether the field **determines** those lines.

Mutate one config path, regenerate, and diff by line content. Every range attributed to that path
must contain at least one line the mutation moved.

```ts
import { matchesConfigPath } from '@openzeppelin/codegen-core';
import type { GenerateOptions, GenerationResult } from '@openzeppelin/codegen-core';

type GenerateFn<TConfig> = (config: TConfig, options?: GenerateOptions) => GenerationResult;

/**
 * Ranges claiming `path` that no mutation of `path` can move.
 *
 * An empty array is the passing result. Throws rather than passing vacuously
 * when handed no mutation, because a check that cannot fail proves nothing.
 */
export function undeterminedRanges<TConfig>(
  generate: GenerateFn<TConfig>,
  config: TConfig,
  path: string,
  mutations: ReadonlyArray<(config: TConfig) => TConfig>
): string[] {
  if (mutations.length === 0) throw new Error(`no mutation supplied for "${path}"`);

  const base = generate(config, { recordProvenance: true });
  if (base.provenance === undefined) throw new Error('generator recorded no provenance');

  const moved = new Set<string>();
  for (const mutate of mutations) {
    const after = generate(mutate(config), { recordProvenance: true });
    for (const [file, text] of Object.entries(base.files)) {
      // `FileTree` values are `string | Uint8Array`; binary files carry no line ranges.
      if (typeof text !== 'string') continue;
      const changed = after.files[file];
      const afterLines = new Set(typeof changed === 'string' ? changed.split('\n') : []);
      text.split('\n').forEach((line: string, index: number) => {
        if (!afterLines.has(line)) moved.add(`${file}:${index + 1}`);
      });
    }
  }

  const findings: string[] = [];
  for (const [file, provenance] of Object.entries(base.provenance.files)) {
    for (const entry of provenance.entries) {
      if (entry.kind !== 'range') continue;
      if (!entry.paths.some((recorded) => matchesConfigPath(recorded, path))) continue;

      let determines = false;
      for (let line = entry.range.start; line <= entry.range.end; line += 1) {
        if (moved.has(`${file}:${line}`)) determines = true;
      }
      if (!determines) findings.push(`${file}:${entry.range.start}-${entry.range.end}`);
    }
  }
  return findings;
}
```

Three things make this work, and skipping any of them makes it decorative:

**Match by line content, never by line number.** Insert one line above a block and every number
below it shifts; a number-based diff reports the whole file as moved and the check passes on
everything.

**Keep the mutation valid.** Generators validate before they generate. Changing a claim topic
without changing the issuer that references it throws instead of producing a comparison — a
mutation that cannot run is a check that never ran.

**Give the check its own negative control.** A version that returns `[]` unconditionally turns every
case green. Assert that a mutation which _cannot_ move a path's lines produces findings:

```ts
import { generate } from '@openzeppelin/codegen-rwa-stellar';
import type { RWAConfig } from '@openzeppelin/rwa-config';

import { undeterminedRanges } from './undetermined-ranges';

export function negativeControl(config: RWAConfig): boolean {
  // A no-op "mutation" moves nothing, so every range claiming the path is undetermined.
  const findings = undeterminedRanges(generate, config, 'token.symbol', [
    (c) => structuredClone(c),
  ]);
  return findings.length > 0;
}
```

On the migrated Stellar generator, `token.symbol`, `token.decimals` and
`identityVerification.claimTopics` all return no findings, and the negative control returns five.
Reinstating the iterator drain on the trusted-issuers heading makes the check report exactly that
one range — it catches the class it was built for.

### An uncovered path is an absent oracle

The check proves nothing about a path nobody thought to mutate, and a path that is attributed but
never mutated is indistinguishable from one that is never attributed at all. That is not a
hypothetical: the operator-role address mis-attribution above survived a green determination
suite for a whole sub-feature, because the suite covered six config paths and that was not one of
them.

So the mutation table is not a list someone maintains — it is checked against the surface:

```ts
it('leaves no focusable path without a mutation', () => {
  expect(focusablePaths(reference()).filter((path) => !covered.has(path))).toEqual([]);
});
```

`focusablePaths` derives the surface _from the config_, mirroring whatever the consumer uses to
decide which paths it can ask about — for the wizard, the binding table that turns a focused input
into a `ConfigPath`. Deriving rather than listing is the point: adding an array entry, a module
config field, or unlocking a control grows the surface automatically and turns the omission red,
instead of leaving a silent hole for the next reader to find in the running app.

Give that assertion its own guard too. An enumeration that quietly collapsed to a handful of
scalars would satisfy it vacuously, so assert the surface actually spans the config's array
families as well.

### What the check will flag that is not a bug

Some ranges are genuinely coarse. A readiness checklist that consults the module list to decide what
to warn about depends on it honestly, even if no configuration you can construct moves a line inside
that block. Record those as known-coarse and move on; do not narrow a range that is telling the
truth. The signal to act on is a range claiming a field whose lines it visibly cannot contain — a
heading, a separator, a preflight check with none of the field's content in it.

## Worked examples

Two migrated templates in the Stellar generator, chosen because they teach different halves of the
problem. Both are real, both are byte-frozen against goldens, and both are readable end to end.

### A push/join script → line builder

[`packages/codegen-rwa-stellar/src/templates/scripts/deploy-sh.ts`](../../../packages/codegen-rwa-stellar/src/templates/scripts/deploy-sh.ts)
— the largest template in the generator: several hundred emitted lines from five families of
helpers. Before the migration it was a `const sections: string[] = []` accumulator with seven config
reads hoisted to the top of the function.

Read it for:

- **The builder as the first statement**, before every binding the function used to hoist, with the
  separator passed explicitly rather than left to match the default by luck.
- **`observe` for values used more than once** — the deployment target, admin and manager addresses
  — each passing `.paths` to every line it shapes, including the second, less obvious one (the
  `export STELLAR_ACCOUNT=<identity-for-…>` hint line reuses the admin address and carries its
  paths).
- **Per-occurrence observation of a config array.** `observeSelectedModules` observes
  `compliance.modules[i].moduleId` one index at a time and keys the result by module id. Observing
  the list as one value would give every module's deploy section the union of every module's paths.
- **Live reads at the emit site** for values used once: token name and symbol are read inside the
  template literal of the line they title.
- **Sink threading into helpers**, which is where hazard 4 was fixed —
  [`deploy-sh-post-deploy.ts`](../../../packages/codegen-rwa-stellar/src/templates/scripts/deploy-sh-post-deploy.ts)
  takes a `LineSink` and emits per site, and its indexed loops are hazard 1's fix in place.

### A patched contract source → patch builder

[`packages/codegen-rwa-stellar/src/templates/contracts/rwa-token.ts`](../../../packages/codegen-rwa-stellar/src/templates/contracts/rwa-token.ts)
— the only core contract that reads config at all. It starts from upstream Rust source and applies
exact-match patches for decimals, configured roles and optional document-manager support.

Read it for:

- **`createPatchBuilder` as the first toucher of the scope**, wrapping the upstream text.
- **One `observe` per method guard rather than one for all of them**, so a role attributes to the
  method it actually guards and not to its siblings.
- **A conditional edit that still carries its paths.** The macro import is narrowed only when no
  configured role produced a role guard, and that edit carries the paths consulted to build every
  guard — the read that _decided nothing changed_ is still a dependency.
- **Patch sinks in helpers**, in
  [`rwa-token-patches.ts`](../../../packages/codegen-rwa-stellar/src/templates/contracts/rwa-token-patches.ts),
  including no-op guards emitting `replaceExact(search, search, paths)` so a value that happens to
  match upstream does not silently lose its dependency.

### Keeping the pre-migration signature

Both files end the same way, and it is worth copying:

```ts
import { createProvenanceCollector } from '@openzeppelin/codegen-core';
import type { ProvenanceScope } from '@openzeppelin/codegen-core';

/**
 * Run a scope-aware template outside a generation call, recording nothing.
 *
 * A disabled collector hands the template the raw config and records nothing, and
 * recording never changes a byte — so the text is identical either way, and the
 * template has exactly one implementation.
 */
export function renderDetached<T extends object>(
  config: T,
  filePath: string,
  produce: (scope: ProvenanceScope<T>) => string
): string {
  return createProvenanceCollector(config, { enabled: false }).record(filePath, produce);
}
```

The migrated template takes a scope; the original `(config) => string` export stays, delegating
through this. Existing unit tests and any consumer holding the old signature keep working, and there
is still only one copy of the template. The alternative — an optional scope parameter, or a second
plain-text renderer kept in sync — is a shadow emitter that will drift.

## Checklist

Before calling a template migrated:

- [ ] The builder is the first statement, and the separator is passed explicitly if it is not `'\n'`.
- [ ] `pnpm lint` is clean, so `provenance/no-early-config-read` has nothing left to report.
- [ ] Every `for…of` over a config array is an indexed loop against an observed count.
- [ ] Every possibly-empty interpolation in a block contributes its paths conditionally — **all** of
      them, not just the first one you found.
- [ ] Every `observe` callback was audited for what it _reaches_, not what it returns.
- [ ] Every helper answering a question about ONE entry tests before it resolves, so it does not
      read the whole collection to filter it afterwards.
- [ ] Every list scan that only needed a match omits the list root with `omitExactConfigPath`
      before the path list reaches the emit — and whole-list dependence leaves the root alone.
- [ ] The determination check covers **every** path the consumer can ask about, asserted against a
      derived surface rather than a hand-kept list.
- [ ] Every membership array and optional scalar has both a value mutation and an absence mutation.
- [ ] Every helper that emits more than one line takes a `LineSink` or `PatchSink`.
- [ ] The output is byte-identical to the pre-migration text, asserted, not assumed.
- [ ] A determination check runs over the fields that matter, with a negative control proving it can
      fail.
- [ ] You swept the file for siblings of every hazard you fixed.

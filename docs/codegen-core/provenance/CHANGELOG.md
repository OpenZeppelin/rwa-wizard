# Changelog — provenance capability

Package-level release notes are generated from `.changeset/` into
`packages/codegen-core/CHANGELOG.md`. This file tracks the provenance documentation set.

## Unreleased (minor: `@openzeppelin/codegen-core` 0.1.0 → 0.2.0) — 2026-08-29

### Added

- `GenerateOptions.recordProvenance?: boolean` — ask a generator to record which config paths each
  emitted file read.
- `GenerationResult.provenance?: ProvenanceResult` — the answer, present only when asked for and
  supported. `hasProvenance(result)` is the presence test; `ProvenanceGenerationResult` the
  narrowed type.
- `createProvenanceCollector(config, { enabled })` with `ProvenanceCollector` (`record`,
  `createFile`, `observe`, `result`, `enabled`), `ProvenanceScope` (`filePath`, `config`, `drain`, `addRange`),
  `RecordOptions` (`createdBy`), `ProvenanceCollectorOptions`.
- `createConfigRecorder(config)` with `ConfigRecorder` (`view`, `drain`, `all`) and the frozen
  `CONFIG_RECORDER_PROBE_KEYS` (`toJSON`, `then`).
- Path algebra: `ConfigPath`, `ROOT_CONFIG_PATH` (`''`), `ConfigPathSegment`, `parseConfigPath`,
  `formatConfigPath`, `matchesConfigPath`.
- Result types and helpers: `ProvenanceEntry` (`file` | `range` | `created`),
  `PROVENANCE_ENTRY_KINDS`, `ProvenanceEntryKind`, `ProvenanceLineRange`, `FileProvenance`,
  `ProvenanceResult`, `Observed`, `isProvenanceEntry`, `mergeProvenance`, `filterProvenanceByPath`.
- Errors: `ProvenanceViewMutationError` (`code: 'PROVENANCE_VIEW_MUTATION'`),
  `ProvenanceScopeError` (`code: 'PROVENANCE_SCOPE'`, `reason: 'nested' | 'closed'`), and their
  `ProvenanceViewMutation` / `ProvenanceScopeErrorReason` types.
- Line attribution: `createLineBuilder(scope, { separator })` with `LineBuilder` (`config`,
  `observe`, `lineCount`, `text`), `LineSink` (`line`, `lines`, `block`) and `LineBuilderOptions`;
  `createPatchBuilder(scope, source)` with `PatchBuilder` (`config`, `observe`, `current`, `text`)
  and `PatchSink` (`replaceExact`, `insertBeforeExact`, `insertAfterExact`). Documented in
  [line-attribution.md](./line-attribution.md).
- `ProvenanceAttributionError` (`code: 'PROVENANCE_ATTRIBUTION'`; `reason` is
  `'reads-before-builder'`, `'builder-exists'`, `'emit-after-text'` or
  `'secondary-not-attributed'`; plus `filePath` and `paths`) and
  `ProvenanceAttributionErrorReason`.
- Attribution significance: an optional `secondaryPaths?: readonly ConfigPath[]` on the `range`
  variant of `ProvenanceEntry`, written by `ProvenanceScope.addRange(range, paths, options)` via
  the new `AddRangeOptions`, declared ergonomically per emission by `EmitOptions.secondary` on
  `LineSink.line` / `lines` / `block`, and read by `isSecondaryAttribution(entry, query)`.
  Documented in [significance.md](./significance.md).
- `provenance/no-early-config-read` — a repo ESLint rule (`.eslint/plugin-provenance.cjs`), wired
  for `packages/codegen-*/src/**/*.ts` with `{ configTypes: ['RWAConfig'] }`. Not a package export;
  it ships with the repo, not with `@openzeppelin/codegen-core`.

### Changed

- Nothing. `Generator<TConfig>`, `generateZip`, `ZipResult`, `replaceExact`, `insertBeforeExact`,
  `insertAfterExact`, and every previously exported member are unchanged. `GenerationResult` gains
  an optional member only.
- `ProvenanceScope.addRange` and `LineSink.line` / `lines` / `block` each gain one **optional
  trailing** parameter. Every existing call compiles and behaves identically, and a generator that
  passes neither produces byte-for-byte the same `ProvenanceResult` object it produced before —
  no `secondaryPaths` member appears anywhere.

### Guarantees

- Recording never changes generated bytes or `metadata.configHash`, on any generate path.
- A path is attributed to a file only if it was read through that file's scope view or attached
  with `addRange`/`createdBy`. Reads on the raw config attribute to nothing.
- A read records its path regardless of the value read (`''`, `false`, `0`, `null`, absent).
- Reported sets are pruned: a traversal on the way to a recorded descendant is dropped; a terminal
  read (leaf, `has`, enumeration) never is. A scope that read only `settings.name`
  does not answer `settings.symbol`; one that read `settings` as an object answers every `settings.*`.
- Provenance carries paths, never config values; error messages and lint reports likewise —
  including `secondary-not-attributed`, which names only the offending paths.
- Significance defaults to primary **structurally**. No value holds `'primary'`; the sole writer of
  `secondaryPaths` is the `addRange` call that created the entry. There is no setter, no post-pass,
  no default-filling, and `mergeProvenance` returns input entries by reference, so no code path can
  invent a demotion.
- A recorded `secondaryPaths` is canonical: either absent, or a non-empty sorted duplicate-free
  subset of the entry's own `paths`. `[]` is never recorded. `file` and `created` entries never
  carry it.
- `EmitOptions.secondary` applies to the call it is passed to and to nothing else: it is never
  pending, so a zero-line emission carries its paths forward and discards the mark, and an
  emission with an empty path union records no entry at all.
- `secondary-not-attributed` fires whether or not recording is enabled, and before any state is
  written — a rejected `addRange` records nothing and leaves the scope usable.
- `isSecondaryAttribution` answers per attribution, not per entry: `true` iff the entry is a marked
  range that matches the query and **every** matching path is secondary. It never contradicts
  `filterProvenanceByPath` about whether an entry matches.
- Marking changes no generated byte and no recorded range or `paths` array; it is metadata only.
- The recording view is read-only; every mutation throws.
- `LineBuilder.text()` is exactly `elements.join(separator)`; `PatchBuilder.text()` is exactly the
  sequential result of the same `replaceExact` / `insertBeforeExact` / `insertAfterExact` calls.
  Attribution adds no bytes.
- A builder never drops, prunes, filters, reorders-with-loss, or invents a path; every string
  handed to it comes back out.
- Builder guards (`reads-before-builder`, `builder-exists`, `emit-after-text`) fire whether or not
  recording is enabled, so misuse surfaces in tests that never turn it on. Emits and patches are
  atomic: a throw leaves the builder exactly as it was.
- Patch regions resolve against the final text and survive every later edit; upstream lines that
  were never edited carry no attribution.
- No dependency added; `ES2020` lib only; browser-safe; no logging. The only module state in the
  builders is a `WeakSet` enforcing one builder per scope — unobservable, retaining nothing, and
  changing no output.

### Migration

- **Consumers:** none required. To use the capability, pass `{ recordProvenance: true }` and
  presence-test with `hasProvenance`. Do not assume the field is present.
- **Generator authors:** none required to keep compiling. To adopt, follow
  [integration-guide.md § Migrating an existing generator](./integration-guide.md#migrating-an-existing-generator):
  create one collector after validation, produce every file inside `collector.createFile`, keep
  validation and hashing on the raw config, attach `collector.result()` when defined, and add the
  three honesty tests.
- **Generator authors declaring significance:** nothing is required — unmarked is primary and
  remains a complete, well-formed result. To adopt, read
  [significance.md](./significance.md) and mark at the emission (`sink.lines(text, paths,
{ secondary: true })`), never on the helper that formats display text.
- **Consumers of provenance:** nothing is required. To use significance, call
  `isSecondaryAttribution(entry, query)`; do not read `secondaryPaths` directly, and do not treat
  an unmarked entry as anything but primary. If provenance crosses a trust boundary, canonicalise
  a mark by intersecting it with the entry's `paths` rather than rejecting the entry.
- **Template authors adopting line attribution:** follow
  [line-attribution.md § Migrating a template](./line-attribution.md#migrating-a-template). Take
  the scope rather than the config, create the builder as the first statement, replace the
  string accumulator, then push every hoisted config read down to its emit site — `pnpm lint`
  names the ones that remain. Pass a non-default `separator` explicitly; it is the only migration
  mistake that changes bytes. Assert the new `text()` equals the previous `join` before trusting
  any range, and prove the attribution separately — see
  [attribution-hazards.md](./attribution-hazards.md).

### First adopter

`@openzeppelin/codegen-rwa-stellar` implements the capability on both its generate paths — plain and
identity-support — at line level, across every template. No generated byte and no `configHash`
changed, and the package's root exports are unchanged. Internally, every migrated template keeps its
`(config) => string` signature by delegating to a scope-aware implementation through a disabled
collector, so there is one copy of each template and existing callers were untouched.

- Ask for it the same way as any generator: `generate(config, { recordProvenance: true })`, then
  `hasProvenance(result)`. Without the flag the result has no `provenance` key at all.
- Files that read no config report a `file` entry with empty `paths` rather than going unrecorded —
  an honest "nothing depends on this", distinct from a file emitted outside a scope.
- Configuration the generator only validates is attributed to no file. Administrative controls, for
  instance, appear in no entry but the serialised configuration dump, which depends on every leaf.
- Files whose existence is decided by config (the per-module contract crates) carry a `created`
  entry naming the individual selection that created them, not the module list.
- It declares significance on the two generated shell scripts and nowhere else, through three
  emitting display helpers that are the only sites in the package where a mark is written. The
  pure `shellEcho` / `shellSection` / `shellSubsection` formatters stay unmarked on purpose: their
  output is usually co-emitted with the deploy command it announces, so a formatter-level mark
  would have demoted the ranges that determine the deployment. A test-owned display grammar
  asserts the biconditional over every recorded range in both scripts, and that no mark exists
  outside them.

### Known limitation

- A **mixed-significance** entry — one `range` whose `secondaryPaths` is a _proper_ subset of its
  `paths` — is expressible through `addRange` and answered correctly by `isSecondaryAttribution`,
  and both are covered by tests that construct the shape directly. **No current generator produces
  one:** `EmitOptions.secondary` expands uniformly across an emission's whole path union, so every
  entry the Stellar generator records is wholly marked or unmarked, asserted across the golden
  matrix. The shape is specified and queryable, not exercised end to end.

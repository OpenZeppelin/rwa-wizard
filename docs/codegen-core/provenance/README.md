# Provenance

> An optional capability on the `@openzeppelin/codegen-core` generator contract that answers
> "which config fields did each generated file read?" — recorded while the generator runs, not
> inferred afterwards.

## Overview

Provenance is for anyone writing a generator against `@openzeppelin/codegen-core` (the next
chain package, a CLI, an agent) and for anyone consuming a `GenerationResult` who wants to map a
configuration field to the files, and optionally the lines, it determines. A caller asks with
`GenerateOptions.recordProvenance: true`; a generator that supports the capability answers with
`GenerationResult.provenance`; a generator that does not simply ignores the flag and returns the
same result it always did. Nothing on the `Generator` interface changes, and recording never
changes a single generated byte or the `configHash`.

The mechanism is a recording view of the config. The generator produces each file inside a
scope; inside that scope it reads the config through a `Proxy` that logs every property path it
touches. Whatever a file's template read is, by definition, what that file depends on. There is no
text search, no regenerate-and-diff, and no heuristics.

The single most important thing to know: **only reads made through a scope's view are recorded,
and only to that scope's file.** Validation and hashing must run on the raw config, outside every
scope, so that a field consulted only by a validator (a locked control, a policy switch) is
attributed to no file. Whole-run recording gets this wrong — every file appears to depend on
every field the validator touched — and that is the failure this design exists to prevent. See
[Safety](#safety).

## Quick Start

```bash
pnpm add @openzeppelin/codegen-core
```

### Ask for provenance

```ts
import { filterProvenanceByPath, hasProvenance } from '@openzeppelin/codegen-core';
import type { GenerationResult, Generator } from '@openzeppelin/codegen-core';

export function filesDependingOn<TConfig>(
  generator: Generator<TConfig>,
  config: TConfig,
  fieldPath: string
): string[] | undefined {
  const result: GenerationResult = generator.generate(config, { recordProvenance: true });
  if (!hasProvenance(result)) return undefined; // this generator does not record provenance
  return Object.keys(filterProvenanceByPath(result.provenance, fieldPath).files);
}
```

`hasProvenance` is the whole detection story: a `true` means this result carries provenance; a
`false` means the generator did not record it. There is no static flag to check and no method to
probe for.

### Record provenance in a generator

```ts
import {
  computeConfigHash,
  createProvenanceCollector,
  mergeFileTrees,
} from '@openzeppelin/codegen-core';
import type {
  FileTree,
  GenerateOptions,
  GenerationResult,
  Generator,
  ValidationResult,
} from '@openzeppelin/codegen-core';

interface MyConfig {
  settings: { name: string; symbol: string };
  members: Array<{ address: string }>;
  locked: { policy: string };
}

export class MyGenerator implements Generator<MyConfig> {
  readonly name = 'my-generator';
  readonly version = '1.0.0';

  validate(config: MyConfig): ValidationResult {
    const errors =
      config.locked.policy.length === 0
        ? [{ field: 'locked.policy', code: 'REQUIRED_FIELD', message: 'policy is required' }]
        : [];
    return { valid: errors.length === 0, errors, warnings: [] };
  }

  generate(config: MyConfig, options?: GenerateOptions): GenerationResult {
    // 1. Validate on the RAW config. These reads attribute to nothing.
    const validation = this.validate(config);
    if (!validation.valid) throw new Error('Invalid config');

    // 2. One collector per generate() call, enabled iff the caller asked.
    const provenance = createProvenanceCollector(config, {
      enabled: options?.recordProvenance === true,
    });

    // 3. Produce every file inside its own scope, reading through `scope.config`.
    const files: FileTree = mergeFileTrees(
      provenance.createFile('NAME.txt', ({ config: c }) => c.settings.name),
      provenance.createFile('members.txt', ({ config: c }) =>
        c.members.map((m) => m.address).join('\n')
      )
    );

    // 4. Hash on the RAW config. Then attach the result — `undefined` when disabled.
    const result: GenerationResult = {
      files,
      metadata: {
        generatorName: this.name,
        generatorVersion: this.version,
        generatedAt: new Date().toISOString(),
        fileCount: Object.keys(files).length,
        configHash: computeConfigHash(config),
      },
    };
    const recorded = provenance.result();
    return recorded === undefined ? result : { ...result, provenance: recorded };
  }
}
```

Run with `{ recordProvenance: true }` and the result carries:

```jsonc
{
  "files": {
    "NAME.txt": { "entries": [{ "kind": "file", "paths": ["settings.name"] }] },
    "members.txt": {
      "entries": [
        {
          "kind": "file",
          "paths": ["members", "members[0].address", "members[1].address"],
        },
      ],
    },
  },
}
```

`locked.policy` appears nowhere, because only `validate` read it and `validate` ran on the raw
config. That is the property the scoping discipline buys. Note that `NAME.txt` reports
`settings.name` only — the `settings` step on the way to it is a traversal and is pruned — while
`members.txt` keeps `members` because `.map` reads the array itself.

## Key Concepts

**Recorded, not inferred.** A file's dependencies are exactly the config paths its template read
while producing it. A read records regardless of the value — `''`, `false`, `0`, `null`, and
absent optional keys all record — because the generated text depends on the field either way.
Nothing in the result is a value; only paths.

**Config paths.** A path is a string in the same dialect `ValidationError.field` already uses:
dot-separated keys, numeric indices in brackets — `settings.name`, `members[1].address`. The empty
string `''` is the root, meaning "the whole config was read" (this is what `JSON.stringify(config)`
records). `matchesConfigPath` defines the one matching rule: two paths match when they are equal
or one is a segment-boundary prefix of the other, so a recorded `settings` answers a query for
`settings.name`, a recorded `members[1].address` answers a query for `members[1]`, and
`settings.nameX` never answers `settings.name`.

**Traversal versus terminal reads.** Walking through an object on the way to a leaf
(`c.settings.name`) is a _traversal_ of `settings`; reading a value, testing a key, or enumerating
an object (`c.settings.name`, `'x' in c.settings`, `Object.keys(c.settings)`, `JSON.stringify(c.settings)`)
is a _terminal_ read. When a scope reports its paths, a traversal is dropped if a strict descendant
was also read in that scope; a terminal read is never dropped. So a scope that read only
`settings.name` reports `['settings.name']` and does **not** answer a query for `settings.symbol`,
while a scope that read `settings` as an object (`Object.keys`, `JSON.stringify`, or a bare
`c.settings` with nothing read beneath it) reports `settings` and matches every `settings.*` query, present or absent — which is
correct, because its output depends on the whole object.

**Per-file scopes.** `createProvenanceCollector(config, { enabled })` gives a generator one
collector per `generate()` call. `collector.createFile(path, scope => text)` produces one file
under its own recording scope; `collector.record(path, scope => value)` is the same for values
that are not a single file. Scopes do not nest and are synchronous. Reads on the raw config, reads
in another scope, and reads through `collector.observe` attribute to nothing.

**Three entry kinds.** Each recorded file gets exactly one `file` entry (every path read), zero or
one `created` entry (the paths the generator read to decide the file exists — pass them as
`createdBy`, usually from `collector.observe(...).paths`), and zero or more `range` entries (the
paths behind a 1-indexed inclusive line range, attached with `scope.addRange`). `isProvenanceEntry`
is the structural guard for untrusted shapes.

**Optional, detected by presence.** `recordProvenance` is an ordinary optional member of
`GenerateOptions`; `provenance` is an ordinary optional member of `GenerationResult`. Existing
generators compile and behave unchanged. Consumers call `hasProvenance(result)`; nothing throws
when the capability is absent.

**Line attribution is a builder, not a search.** `createLineBuilder` and `createPatchBuilder` turn
a scope into a stream of attributed emissions, computing each range from the text they are about
to produce rather than by searching the finished output. They carry one rule: **a config read must
happen at the emit site, not before it** — a value read early and emitted late is attributed to
the line that was current when it was _read_. See [line-attribution.md](./line-attribution.md).

**Significance is declared, and primary is structural.** A `range` may carry an optional
`secondaryPaths` subset marking the attributions that merely _display_ a value rather than
determine it — the deploy command that uses the configured owner address is primary; the `echo`
that prints the same address as an example is secondary. Absence means primary, no value anywhere
holds `'primary'`, and the only writer is the `addRange` call that created the range, so a
generator that marks nothing produces exactly the result it always did. Consumers **read**
significance with `isSecondaryAttribution` and never compute it. See
[significance.md](./significance.md).

## Attribution Hazards

See [attribution-hazards.md](./attribution-hazards.md) before migrating a generator. Byte identity
and honest attribution are independent proofs, and a golden-output suite only sees the first — so
every attribution bug you will write is byte-perfect and golden-green. That page catalogues the
hazard classes the first real migration produced (plus list-scan / hazard 5), each reduced to a
runnable snippet whose broken and fixed versions emit identical text; the differential check that
finds them on purpose; and a guided read of two migrated templates, one per builder. When a list
was walked only to find a match, drop the list root with `omitExactConfigPath` before the emit —
do not change `matchesConfigPath`.

## Claim-topic selection

Selection on `ClaimTopic` is authoring state with no on-chain counterpart. Generators project it
through `selectedClaimTopicIndices` / `selectedClaimTopicIds` inside an `observe` scope. A
recording reader records a read of an absent key, so omit-when-true protects `config.json` bytes
but not provenance output. Full docs:
[claim-topic selection](../../claim-topic-selection/README.md).

## Safety

Read these before wiring the capability into a generator.

- **Validate and hash on the raw config, never on a view.** `validate(config)` and
  `computeConfigHash(config)` must receive the object the caller passed in, outside every scope.
  A read made through `scope.config` is attributed to that scope's file; a read made anywhere
  else is attributed to nothing. Get this backwards and every file will claim to depend on every
  field the validator touched. The generated bytes will not change, so only a provenance test can
  catch it (see the guide's [Prove your adoption is honest](./integration-guide.md#prove-your-adoption-is-honest)).
- **The view is read-only.** Any write, delete, `defineProperty`, `setPrototypeOf`, or
  `Object.freeze` on a view throws `ProvenanceViewMutationError`. `structuredClone(view)` throws a
  `DataCloneError`. Templates must not mutate or clone config; if one does, recording surfaces it
  on the first run.
- **Scopes do not nest and are synchronous.** Calling `record`/`createFile` inside another
  `produce` throws `ProvenanceScopeError('nested')` — even when recording is disabled, so the
  mistake shows up in tests that never turn it on. A `produce` that returns a `Promise` has its
  scope closed before any awaited read runs, and that read throws `ProvenanceScopeError('closed')`.
- **Views do not survive their scope.** A view captured inside `produce` and read after `produce`
  returned throws `ProvenanceScopeError('closed', filePath)`. `observe` and `record` run
  `unwrapDeep` on the value they return: a returned view becomes its raw target, and views nested
  inside plain containers the caller built (`map`/`filter` results, object literals) are unwrapped
  the same way. Non-plain objects (class instances, `Date`, `Map`, …) are left alone. Prefer
  returning primitives or fresh objects from `observe` when you do not need the deep walk.
- **`result()` closes the collector.** Call it once, at the end; any later `record`, `createFile`
  or `observe` throws `ProvenanceScopeError('closed')`.
- **Line ranges are shape-checked only.** `addRange` rejects `start < 1`, non-integers and
  `end < start` with a `RangeError` (even when disabled) but cannot know the final text length
  while `produce` is still running. Positions against the produced text are the caller's
  responsibility. The builders compute correct positions for you — prefer them to raw `addRange`.
- **A config read must happen at the emit site, not before it.** When a template uses a builder, a
  value read early and emitted late is attributed to the line current when it was _read_. Reads
  above the builder throw `ProvenanceAttributionError('reads-before-builder')`; reads below it,
  used after an intervening emission, are silent at runtime and are caught only by the
  `provenance/no-early-config-read` ESLint rule. Hoisting reads to the top of a template is the
  normal shape of existing generator code, so expect to meet this on the first migration. See
  [line-attribution.md](./line-attribution.md).
- **Significance defaults to primary, and nothing can invent a demotion.** A `range` entry is
  secondary for a path only if the `addRange` that created it named that path. There is no setter,
  no post-pass, no default-filling and no merge rule that could produce a mark, and
  `mergeProvenance` returns input entries by reference. A consumer narrowing untrusted provenance
  should repair a malformed mark by **intersecting** it with the entry's own `paths` — which can
  only promote to primary — and never by rejecting the entry, which would cost the user a real
  attribution. See [significance.md](./significance.md).
- **Read significance with `isSecondaryAttribution`, never with `secondaryPaths`.** Queries are
  prefix queries; marks are per exact path. `secondaryPaths.length > 0` demotes a range that
  determines a sibling path, and `secondaryPaths.includes(query)` promotes everything a prefix
  query reaches. The rule is: secondary iff the entry matches **and every matching path** is
  secondary.
- **A mark ranks; it never filters.** A secondary attribution is a true statement that the field
  reaches those lines. Hiding it costs the user information the generated output cannot give back.
- **A green golden suite proves nothing about attribution.** Goldens compare `result.files`;
  `result.provenance` is not in them, and recording is designed never to change output — so every
  wrong range is byte-perfect by construction. Prove byte identity and honest attribution
  separately. See [attribution-hazards.md](./attribution-hazards.md#two-proofs-not-one).
- **Plain JSON shapes only.** The recorder descends into plain objects (prototype
  `Object.prototype` or `null`) and arrays. A `Date`, `Map`, `Set`, typed array, class instance or
  function is recorded at the path it sits on and returned raw; reads inside it are not tracked.
  Configs that are schema-first JSON — the shape the constitution requires — are fully covered.
- **Keys the dialect cannot carry fall back to the parent.** A key that is empty or contains `.`,
  `[` or `]` records the parent path and returns the raw value. Non-ASCII keys are fine.
- **A missing key is a gap, not "depends on nothing".** A path present in `result.files` but
  absent from `result.provenance.files` means the generator emitted that file outside any scope.
  A file that genuinely reads no config has a `file` entry with empty `paths`.
- **An absent optional key still records.** `ClaimTopic.selected` omitted means selected, and a
  selection walk records `claimTopics[i].selected` on every topic anyway. Omit-when-true protects
  generated `config.json` bytes, not provenance. See
  [claim-topic selection](../../claim-topic-selection/README.md).
- **The ZIP path is unaffected.** `generateZip` accepts a result with or without provenance and
  produces the same archive; `ZipResult` carries no provenance.
- **Cost.** Recording adds roughly 0.1–0.2 ms to a sub-millisecond generate and allocates one
  `Proxy` per distinct plain object or array actually read. There is no progress phase for it.

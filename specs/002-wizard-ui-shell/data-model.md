# Data Model: RWA Wizard UI Shell

## Overview

The UI shell stores user intent and orchestration state, not generated artifacts. The canonical draft payload is `RWAConfig`; all app-local entities either wrap that config for persistence and UX, or describe available targets and generation status.

## Entities

### 1. `WizardDraftRecord`

Represents one persisted wizard draft stored in client-side IndexedDB.

| Field         | Type                                                           | Required | Notes                                                  |
| ------------- | -------------------------------------------------------------- | -------- | ------------------------------------------------------ |
| `id`          | `string`                                                       | Yes      | Primary identity generated by storage/repository layer |
| `title`       | `string`                                                       | Yes      | User-visible draft name                                |
| `targetId`    | `string`                                                       | Yes      | Selected target ecosystem, initially `stellar`         |
| `status`      | `'draft' \| 'ready' \| 'generating' \| 'generated' \| 'error'` | Yes      | High-level lifecycle state                             |
| `currentStep` | `WizardStepId`                                                 | Yes      | Last active wizard stage                               |
| `config`      | `RWAConfig`                                                    | Yes      | Canonical persisted wizard payload; future deployment UI must write `deployment.target` references, not a raw network string |
| `metadata`    | `WizardDraftMetadata`                                          | Yes      | UI-only flags and provenance                           |
| `createdAt`   | `Date`                                                         | Yes      | Storage-managed                                        |
| `updatedAt`   | `Date`                                                         | Yes      | Storage-managed                                        |

#### Validation rules

- `title` must be non-empty once a draft is persisted.
- `targetId` must reference a visible target catalog entry.
- `config` must remain serializable for storage and import/export.
- If a future deployment placeholder is enabled, `config.deployment.target` must remain a valid preset/custom `DeploymentTarget` reference shape.
- `status = 'ready'` is allowed only when blocking validation errors are absent.
- `status = 'generating'` is transient and must revert to `ready`, `generated`, or `error`.

### 2. `WizardDraftMetadata`

Stores non-domain UI data that should not pollute `RWAConfig`.

| Field               | Type                                   | Required | Notes                                                              |
| ------------------- | -------------------------------------- | -------- | ------------------------------------------------------------------ |
| `isManuallyRenamed` | `boolean`                              | Yes      | Prevents autosave from regenerating titles                         |
| `importSource`      | `'manual' \| 'imported' \| 'template'` | Yes      | Origin of the draft                                                |
| `schemaVersion`     | `string`                               | Yes      | Import/export and migration support                                |
| `lastOpenedAt`      | `Date`                                 | No       | Useful for sorting/resume UX                                       |
| `mockCoverage`      | `string[]`                             | No       | Optional tags for known mock-backed gaps used by the draft/session |

#### Validation rules

- `schemaVersion` must be present on every exported/imported draft.
- Imported drafts set `importSource = 'imported'`.
- `mockCoverage` contains only identifiers from the mock gap register if used.

### 3. `DraftListItem`

A lightweight projection of persisted drafts used for list views.

| Field       | Type                       | Required | Notes                            |
| ----------- | -------------------------- | -------- | -------------------------------- |
| `id`        | `string`                   | Yes      | Draft identifier                 |
| `title`     | `string`                   | Yes      | Display name                     |
| `targetId`  | `string`                   | Yes      | Used for badges/icons            |
| `status`    | `WizardDraftRecord.status` | Yes      | Display-only summary             |
| `updatedAt` | `Date`                     | Yes      | Sorting and recent list behavior |

### 4. `TargetCatalogEntry`

Represents one target ecosystem displayed in the sidebar selector.

| Field                 | Type                  | Required | Notes                                        |
| --------------------- | --------------------- | -------- | -------------------------------------------- |
| `id`                  | `string`              | Yes      | Stable target key such as `stellar` or `evm` |
| `name`                | `string`              | Yes      | User-facing label                            |
| `description`         | `string`              | Yes      | Short selector description                   |
| `icon`                | `string` or asset ref | Yes      | Selector-safe icon metadata                  |
| `enabled`             | `boolean`             | Yes      | Selectable or disabled                       |
| `showInUI`            | `boolean`             | Yes      | Hidden vs visible-disabled distinction       |
| `disabledLabel`       | `string`              | No       | Example: `Coming Soon`                       |
| `disabledDescription` | `string`              | No       | Reason shown in selector/details             |
| `packageName`         | `string`              | Yes      | Expected codegen package/runtime source      |

#### Validation rules

- Entries with `enabled = false` may still appear if `showInUI = true`.
- Only enabled entries may be selected for draft creation.
- First iteration must include one enabled entry: `stellar`.

### 5. `TargetCapabilitySnapshot`

Describes what the currently selected target exposes to the wizard UI at runtime.

| Field              | Type                       | Required | Notes                                                        |
| ------------------ | -------------------------- | -------- | ------------------------------------------------------------ |
| `targetId`         | `string`                   | Yes      | Matches `TargetCatalogEntry.id`                              |
| `availableModules` | `ComplianceModuleOption[]` | Yes      | Used to populate compliance UI                               |
| `networkOptions`   | `TargetNetworkOption[]`    | No       | Reserved for a future feature-flagged deployment placeholder |
| `mocked`           | `boolean`                  | Yes      | Indicates real vs mock-backed capability source              |

#### Validation rules

- `availableModules` should expose all modules from the target's registry (both stable and under-review), each including `requiredHooks`, `review` state, and `configFields` metadata.
- `networkOptions` may be omitted in the MVP default-flag state and are only consumed if a future deployment placeholder is enabled.
- When consumed by a future deployment placeholder, `networkOptions` must map into `config.deployment.target` as preset/custom references rather than a legacy `deployment.network` string.
- `mocked = true` requires an entry in the mock gap register.

### 6. `GenerationJobState`

Tracks the most recent generation attempt for the active draft.

| Field          | Type                                                                            | Required | Notes                             |
| -------------- | ------------------------------------------------------------------------------- | -------- | --------------------------------- |
| `draftId`      | `string`                                                                        | Yes      | Source draft                      |
| `phase`        | `'idle' \| 'validating' \| 'generating' \| 'packaging' \| 'success' \| 'error'` | Yes      | UI-facing async phase             |
| `startedAt`    | `Date`                                                                          | No       | Set when generation begins        |
| `completedAt`  | `Date`                                                                          | No       | Set on success or failure         |
| `zipFileName`  | `string`                                                                        | No       | Present on successful ZIP handoff |
| `errorMessage` | `string`                                                                        | No       | Present on failure                |
| `usedMock`     | `boolean`                                                                       | Yes      | Indicates mock-backed path        |

#### Validation rules

- `zipFileName` is required only when `phase = 'success'`.
- `errorMessage` is required only when `phase = 'error'`.
- `usedMock = true` requires a matching mock gap entry.

### 7. `MockGapRecord`

Documentation-facing entity that tracks temporary generator gaps bridged by app-local mocks.

| Field                | Type     | Required | Notes                                            |
| -------------------- | -------- | -------- | ------------------------------------------------ |
| `id`                 | `string` | Yes      | Stable identifier                                |
| `targetId`           | `string` | Yes      | Affected target                                  |
| `capability`         | `string` | Yes      | Missing real behavior                            |
| `mockBehavior`       | `string` | Yes      | What the UI uses temporarily                     |
| `replacementTrigger` | `string` | Yes      | Condition for swapping in the real integration   |
| `owner`              | `string` | No       | Optional accountability field for planning/tasks |

## Relationships

- One `WizardDraftRecord` belongs to one `TargetCatalogEntry`.
- One `WizardDraftRecord` wraps one `RWAConfig`.
- One `WizardDraftRecord` may produce many `GenerationJobState` records over time, but the UI typically surfaces the latest one.
- One `TargetCatalogEntry` may expose one `TargetCapabilitySnapshot` at a time per active app session.
- One `MockGapRecord` may be referenced by many drafts or generation jobs if the same temporary gap affects multiple flows.

## State Transitions

### Draft lifecycle

```text
ephemeral new draft
  -> persisted draft
  -> ready
  -> generating
  -> generated
  -> ready (after further edits)
  -> error (if generation fails)
```

Notes:

- A draft begins as ephemeral until meaningful content exists.
- Import creates a new persisted draft directly in `draft` state.
- Deletion is terminal and removes the persisted record.

### Target availability lifecycle

```text
hidden
  -> visible-disabled
  -> enabled
```

Notes:

- The first iteration uses `stellar = enabled`.
- Future ecosystems such as `evm` may start as `visible-disabled` with a coming-soon label.

### Generation job lifecycle

```text
idle
  -> validating
  -> generating
  -> packaging
  -> success
  -> error
```

Notes:

- On failure, the draft itself remains available for editing/export.
- Success results in ZIP delivery rather than persisted artifact storage.

## Derived Validation Rules

- Imported configs must create a new draft rather than overwriting the current draft.
- Unsupported targets cannot be selected even if visible in the target catalog.
- Draft persistence errors must not destroy the in-memory editing session.
- Deployment-placeholder data must not be required for MVP draft validity when its feature flag is disabled.
- The UI shell persists configuration intent only; generated file trees and ZIP blobs are not stored as drafts.
